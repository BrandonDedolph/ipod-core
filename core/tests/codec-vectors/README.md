# Codec test vectors

Committed bytes, not generated at test time: a `sin()` is not required to round
identically across glibc, musl and macOS libm, and an encoder is not required
to produce the same bitstream across versions. Everything here is regenerated
by `../scripts/gen_codec_vectors.sh` when a vector is added or a decoder is
re-vendored, and the `.sha256` beside each file is what a reviewer checks the
committed bytes against.

## Two kinds of MP3 reference, and why they are not interchangeable

A lossless codec has one right answer, so the FLAC vector is compared with
`memcmp` against the PCM that was encoded. MP3 does not: ISO/IEC 11172-4
specifies a *tolerance*, and two correct Layer III decoders are never
bit-identical. So there are two references and they answer different
questions.

**`*.mp3.ref.pcm` — the regression pin.** PCM captured from OUR decoder
(`codecs/pvmp3` through `codecs/pvmp3/mp3.c`) at fixture time by
`../scripts/capture_mp3_ref.c`. `codec-kat` and `mp3-freestanding` memcmp
against it. It catches any change to the vendored decoder or the wrapper that
moves a single sample — which is exactly what it is for — and says nothing
whatever about whether the decode is correct.

**`*.ffmpeg.flac` — the truth.** ffmpeg's decode of the same `.mp3`, stored as
FLAC because that is lossless and half the size (`mp3-accuracy` decodes it with
the tree's own dr_flac). `mp3-accuracy` compares against it to a tolerance:
PSNR at least 96 dB and a peak error of at most 2 LSB, after aligning the two.
It is the test that would have caught a decoder that was wrong from the start,
which the regression pin would have happily kept passing.

**Do not "fix" a one-LSB difference.** The exact-match reference is captured
from the HOST build, which uses pvmp3's C-equivalent fixed-point ops. The ARM
build uses the `smull` assembly in `codecs/pvmp3/upstream/asm/`, and the two
round differently by design — measured at 101.6 dB / 1 LSB and 103.4 dB /
2 LSB against ffmpeg respectively, both comfortably inside the standard. The
ARM build is therefore held only to the tolerance test; it is not, and cannot
be, bit-compared against a reference captured on the host.

**Why the comparison is offset-aligned.** ffmpeg applies the LAME encoder
delay and end padding (gapless trimming) to its output; we deliberately do not
— gapless is out of scope, and the delay and padding are read only to correct
the reported LENGTH so it matches ffprobe and the host index. The two decodes
of the same file therefore start about 1105 samples apart by design. The
accuracy suite finds that offset by correlation and asserts it is small; an
alignment of thousands of samples would be a framing bug and fails the test.

## The vectors

| file | what it is |
|---|---|
| `sine_440hz_1s_44k_s16_stereo.pcm` | 1 s of a 440 Hz sine, s16le 44.1 kHz stereo, generated by `../scripts/gen_codec_vectors.py` |
| `sine_440hz_1s_44k_s16_stereo.flac` | the same, encoded with `flac`. The FLAC KAT round-trips it exactly |
| `sine_440hz_1s_44k_s16_stereo_128k.mp3` | the same, encoded at 128 kbps CBR. Carries an Info tag with an encoder delay of 576 and 1404 of padding, so it is also the fixture for the delay/padding arithmetic |
| `sine_440hz_1s_44k_s16_stereo_128k.mp3.ref.pcm` | our decode of it — 40 frames x 1152, the Info frame stepped over |
| `beethoven_2s_cbr128_44k_stereo.mp3` | 2 s of real music, LAME 128 kbps CBR, 44.1 kHz joint stereo |
| `beethoven_2s_vbr_v5_44k_stereo.mp3` | the same 2 s, LAME `-V 5` VBR — a Xing header with a 100-entry TOC, which is what `mp3-seek` seeks through |
| `beethoven_2s_cbr32_22k_mono.mp3` | the same 2 s as MPEG-2: 22.05 kHz mono, 32 kbps, 576-sample frames, 9-byte side info, and no Xing tag at all, so it exercises the CBR duration estimate |
| `beethoven_*.ffmpeg.flac` | ffmpeg's decode of each, the accuracy reference |

A 440 Hz sine is a poor test of an MP3 decoder — no short blocks, no intensity
stereo, almost no Huffman table coverage — which is why the accuracy and seek
suites use music instead. It stays as the KAT because it is small and it is
what the FLAC vector is made of, so the two codecs are pinned on identical
source audio.

### Provenance of the music

Beethoven, Symphony No. 3 "Eroica", Op. 55, performed by the Czech National
Symphony Orchestra, from the [Musopen
Collection](https://archive.org/details/MusopenCollectionAsFlac) on
Archive.org. **Public domain** — both the composition and this recording.
Reached here by way of the 30 s extract that `esphome-libs/micro-mp3`'s
`examples/decode_benchmark` uses (Apache-2.0, and its README carries the same
attribution); two seconds of it were re-cut, resampled and re-encoded by
`gen_codec_vectors.sh`.

To regenerate these three, point the script at a copy of the recording:

    MUSOPEN_SRC=/path/to/eroica.flac ./core/tests/scripts/gen_codec_vectors.sh

Without `MUSOPEN_SRC` the script leaves them alone and regenerates only the
synthetic vectors, so a routine re-run cannot silently replace the committed
music with silence.
