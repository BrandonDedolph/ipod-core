## (3) The wrapper — one real bug (APE), rest correct

Verified by reading `mp3.c`, `mp3_frame.c`, `id3_meta.c`, the pvmp3 `validate_input()` and mute
path (`pvmp3_framedecoder.c:311-341, 537-600, 753-785`), and by construction:

- Return codes: `DECODER_ERR_INVALID` for no Layer III frame, `_UNSUPPORTED` for 8/11.025/12/16 kHz,
  `_INTERNAL` for alloc/seek failure; decode returns `done` (partial at EOF, then 0), never an error
  for a truncated tail (`mp3_robust_test` "stops at the last whole frame, `n % 1152 == 0`").
- 8–16 kHz refusal: `track_open` returns -1 → `PLAYER_ERR_OPEN`; on a direct play the player stays
  put; during hand-over `player.c:1622-1628` steps past the entry. USER_GUIDE's "appears in the list
  but will not start" is accurate.
- One frame per `pvmp3_framedecoder` call (`mp3.c:194-200`), `inputBufferCurrentLength ==
  frame_bytes`; the staging buffer is `MP3_MAX_FRAME_BYTES = 1441` (the true maximum, not 2 KB) and
  `src_read_exact` loops over the read-ahead's 32 KB block boundaries, so a frame straddling a block
  is not a special case.
- Free format and reserved index rejected at `mp3_header_parse` (`mp3_frame.c:60`), covered by
  `mp3_robust_test:235-248`; MPEG-2.5 parses but is refused at open by rate (all three rates are
  below the WM8758B floor), covered by `mp3_robust_test:180-184`; Layer I/II refused.
- ID3v2: footer flag adds 10 (`mp3_frame.c:116`), chained tags looped (`:262-267`), a tag-level
  unsynchronisation flag is opaque to the tag walk but the audio is still found (framing skips by
  the declared size, which is the post-unsync size — correct). Xing/Info at 4+side-info regardless
  of CRC (LAME's and ffmpeg's rule); VBRI counts at +10/+14; LAME delay/padding at +21; CBR estimate
  when neither. A junk prefix before the first frame is handled by two-header validation and Xing is
  parsed at the frame actually found (`mp3_frame_test` "junk prefix" case).
- Muted frames (reservoir underflow) keep their full `outputFrameSize` and the error is overridden
  (`pvmp3_framedecoder.c:753-756`), so the wrapper's "outputFrameSize is the gate" comment is right.

**S1 (should-fix) — APEv2 footer parsed at the wrong offset and the wrong bit; the test asserts
the wrong layout.** `core/codecs/pvmp3/mp3_frame.c:146-148` reads `flags = le32(f + 16)` and tests
`0x20000000`. In the APEv2 footer, +16 is the *item count* and the flags word is at +20; "tag
contains a header" is bit 31 (`HAS_HEADER`), bit 29 is `IS_HEADER` (always 0 on a footer). Verified
against FFmpeg `libavformat/apetag.c` (`APE_TAG_FLAG_CONTAINS_HEADER (1U<<31)`, fields read as
version/size/count/flags) and mutagen `apev2.py` (`HAS_HEADER = 1<<31`, footer packed `<4I`
version,size,count,flags). Constructed `cbr_ape.mp3` (LAME CBR + a spec-correct APEv2 tag with
header, footer flags `0x80000000` — exactly what mutagen/ffmpeg write) and ran the branch's
`mp3_stream_scan`: `audio_end = 48932`, expected `48900` — the 32-byte `APETAGEX` header is left
inside the audio region. Same bug in Go, `cli/internal/id3/id3.go:186-191`. The unit test
`tests/codecs/mp3_frame_test.c:231-245` builds a 32-byte footer with the flags at +16 and
`f[19] = 0x20 /* has a header */`, i.e. it pins the misreading. Impact today is benign (the decoder
steps through 32 junk bytes at EOF and returns EOS; a CBR-no-Xing duration is 32 bytes long), but it
is a plan-listed edge case (§5.3 step 2), it is wrong against the spec, and a test would keep it
wrong. Correct: `size = le32(f+12)`, `flags = le32(f+20)`, header present iff `flags & 0x80000000`;
fix the fixture to a real 32-byte footer (add the count) in C and Go.

## (4) Seek — correct; measured

- `mp3_seek_offset`: frame 0 → `audio_start` exactly; `pos = target + delay` shifts into the stream
  timeline (right: the TOC is over the untrimmed bytes); TOC interpolation in 1/65536 with a
  monotonic clamp; proportional fallback; clamped to `[audio_start, audio_end-4]`. `raw_frames` vs
  `total_frames` split is sound.
- Warm-up: back off `512 + 4*first.frame_bytes`, `pvmp3_resetDecoder`, decode-and-discard every
  frame up to the landing. Past-end → the loop hits `pos+4 > audio_end`, decode returns 0, no error
  (tested). Seek to 0 is bit-identical to a fresh open (tested).
- CBR without Xing end-to-end (not in the suites): my harness on `lame -t -b 128`: seek to 1.5 s,
  decode to EOS, tail 66 816 frames vs 67 481 expected — 15 ms late, inside tolerance.
- Measured tolerance in `mp3-seek`: landings 15–22 ms late, PSNR ≥ 101 dB; tail-after-seek within
  277 frames. Landings are consistently *late* (resync to the next header at/after `off`), which the
  test's symmetric bound hides but is fine at this size.
- N8 below on the slack derivation; I could not provoke a muted landing (0/94 seeks on each of
  three silence-led VBR files, including a no-Xing `-V0` whose first frame is 104 B).

## (5) Accuracy test — meaningful

Vectors: Musopen Eroica (public domain, recording and composition) via micro-mp3's benchmark clip,
re-cut/re-encoded by `gen_codec_vectors.sh` (needs `MUSOPEN_SRC`; without it the music is left
alone — good). Reference = ffmpeg's decode *of the MP3* stored as FLAC and decoded with the tree's
dr_flac; offset-aligned by correlation with an upper bound of 2000 frames on the alignment so a
framing bug cannot pass as "encoder delay". Gate 96 dB / 2 LSB against measured 101.6 dB / 1 LSB on
the host C path: the 5 dB margin is deliberate (a rounding change in one Q helper is a warning, not
a red build) and a genuinely broken decoder lands tens of dB lower. The ARM `smull` path is held
only to this test (103 dB measured in the plan's emulation), which the vectors README says
explicitly. The mono 22.05 kHz vector has no Xing (104-byte frames cannot hold one) so it also
exercises the CBR estimate, as the README states.

**S2 (should-fix, documentation) — the "byte-identical index" claim has a hole the parity test only
logs.** For an MP3 with no Xing/VBRI header, `build_index.py` stamps `int(ffprobe duration)` and
`core sync` stamps the first-frame CBR estimate; for untagged VBR these differ a lot (my tree:
ours 13 s vs ffprobe 5.8 s on a 4 s `lame -V0 -t` file; 8 vs 5.5 on `-V5 -t`). `parity_test.go:149`
deliberately reports these by name and passes. `cli/internal/cli/index.go:35` ("The output is
byte-identical to tools/build_index.py"), commit 4cf6fce's body and STATUS ("computes the duration
by ffprobe's rule with a parity test against it") state the guarantee without the caveat. Untagged
VBR is rare (LAME writes Xing unless `-t`), so the fix is one sentence in index.go's help, STATUS and
the design doc: "for an MP3 with no Xing/VBRI header both tools estimate, and the estimates differ
for VBR". Alternatively make Go mimic ffmpeg's estimate — not worth it.

## Nits (real, each verified by reading)

- **N3** `core/player/player.c:2230-2237` and `tests/codecs/mp3_seek_test.c:7-8` say the seek
  "decodes one warm-up frame"; `mp3.c:274-293` backs off four frames + 512 B and decodes every frame
  up to the landing. `codecs/README.md` describes it correctly; make the two match it.
- **N4** `core/codecs/pvmp3/mp3.h:22` "~28 KB of state": `pvmp3_decoderMemRequirements()` is
  21 944 B after the BUFSIZE patch (`mp3.c:24` and `pvmp3/README.md` say 21.4 KB / 21944).
- **N5** STATUS.md ("bss is unchanged") and `docs/design/mp3-playback.md:98` ("bss does not
  move"): bss went 12 214 264 → 12 214 784 B (+520 B; `scan_file_t.fmt` × BROWSE_MAX plus
  `decode_rate`). Commit 7be2e6b's message says text 391 576 B; the docs and `size` say 391 564.
- **N6** `Lavf` encoder string: FFmpeg's reader (`mp3dec.c:257-259`) honours delay/padding for
  `LAME`, `Lavc` *and* `Lavf`; `mp3_frame.c:196` and `id3.go:646` accept only the first two. I
  confirmed `ffmpeg -c copy` of an untagged file writes `Lavf` with delay 0, so nothing visible today;
  one string in each place closes it.
- **N7** `id3_meta.c:354` clamps the *declared* tag size to 1 MB before the walk; a 2 MB tag whose
  text frames follow the APIC returns at `size > left` and loses the title, although the APIC is
  skipped by seek at no cost. Cap bytes read (or count skipped bytes separately).
- **N8** `mp3_frame.h:109` says `first` is "the first audio frame's header"; with a Xing/Info frame
  it is that frame's header (`mp3_frame.c:320`). Harmless for rate/version/channels, but `mp3_seek`'s
  back-off `512 + 4*first.frame_bytes` (`mp3.c:274`) then rests on LAME sizing its Xing frame ≥ 156 B;
  a no-Xing VBR file with a 104-byte first frame gets 928 B of back-off, under one 1044 B frame. Not
  provoked in practice (0/94 on three constructed files) — `4*MP3_MAX_FRAME_BYTES + 512` would make
  the guarantee unconditional for a few KB of extra read.
- **N9** `core art --fetch` still lists FLACs only (`cli/internal/cli/art_fetch.go:286-325
  albumFLACs`): it embeds fetched art into FLAC, so an MP3-only album is silently "no FLAC". That is a
  legitimate deferral (no ID3 writer) but, unlike the librarian one, it is stated nowhere. Also
  `syncer.go:149` `ArtOp.SrcFLAC` now holds an MP3 path.
- **N10** `id3_meta.c:363`: a tag-level unsynchronisation flag makes the whole tag opaque. Right for
  v2.3 (sizes are pre-unsync) but v2.4 frame sizes describe the bytes on disk, so v2.4 text could still
  be read. Documented in the code; a coverage loss on some old iTunes/Winamp libraries.
- **N11** History: five commits where the plan sequenced five PRs is fine, but `7be2e6b` is a rebase
  fix-up ("correct the counts it moved") that belongs squashed into the commits it corrects.
- **N12** Device-bench item, not a code finding: an MP3 open now reads the tail twice (id3_meta_read
  through `meta_ra` on `fat_src` — a forward cluster walk plus a 32 KB block; then
  `mp3_open_stream` through diskbuf — a 32 KB `DISKBUF_SYNC_CHUNK` at the tail before the head refill),
  where FLAC's open seeks to END without reading. `player_probe_meta` does the same per file in the
  no-index scan. Add "MP3 open latency vs FLAC" to the STATUS bench list.
