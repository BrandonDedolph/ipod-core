**N8 seek back-off — changed, but the change does not do what its comment says.**
`mp3.c:269-276` now backs off `512 + 4 * mp3_avg_frame_bytes()` and explains: "a VBR file that
opens on silence can have a 104-byte first frame and 1044-byte frames where the listener is seeking
to, and four of the former is not even one of the latter". `mp3_avg_frame_bytes()`
(`mp3_frame.c:389-401`) is `audio_bytes / (raw_frames / spf)`. For a file with **no Xing/VBRI count
— which is the only way a VBR file has a 104-byte `first` frame, since LAME's Xing frame is
≥ 156 B — `raw_frames` is itself the CBR extrapolation from the first frame's bitrate
(`mp3_frame.c:356-358`), so the quotient is the first frame's size by construction.** Measured with
the harness: `vbr_sil_noxing.mp3` first 104 → avg **104**; `vbr0_sil_noxing.mp3` 104 → **104**. On the
tagged silence-led file it is 224 against a 417-byte first frame, i.e. the back-off *shrank* from
2180 to 1408 B (still over one 1044 B frame here, but a tagged file that is mostly silence with a
320 kbps section would go under it). The muted-landing census is unchanged (0/94 on all three files,
frames ≤ 835 B), so nothing regressed and nothing I can construct with LAME fails; but the comment
claims a guarantee the arithmetic cannot deliver, and `mp3_frame_test.c`'s new case only checks a CBR
file where mean == first. Correct: back off `512 + 4 * MP3_MAX_FRAME_BYTES` (6276 B, ≈ 5 extra frame
decodes per seek, ~25 ms of CPU) which is unconditional, or keep the mean but say in the comment that
it is only a mean when the file states a frame count. **should-fix** (a stale claim in a hot comment,
low impact).

## N8 — fixed

`mp3.c:277`: `back = 512u + 4u * MP3_MAX_FRAME_BYTES` (6276 B), `mp3_avg_frame_bytes()` deleted
from `mp3_frame.c/.h`, `first`'s comment now says "do not size a read against it". The new

frame's length) with the reason in the comment, so nobody reintroduces a per-file "mean". The

## One wording slip, fix in passing

`mp3.c:279` ("four frames at 320 kbps"), STATUS.md:59 ("four frame decodes at 320 kbps") and, by
implication, the "four maximum-size frames" phrasing: 6276 B is four frames only at 32 kHz, where a
320 kbps frame is 1441 B. At 44.1 kHz a 320 kbps frame is 1044 B, so the back-off is **six** frame
decodes there (and 15 at 128 kbps, which is stated correctly). The constant is right; the cost
estimate in the prose understates it by two frames. A two-word change in two files.
